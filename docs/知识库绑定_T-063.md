# 知识库空间绑定与会话继承（T-063）

## 1. 结论先行

1. 控制面新增 `/api/v1/knowledge-bases`（创建/列表/启停）与 `/api/v1/knowledge-bindings`（绑定/查询/解绑），绑定范围**只允许部门或项目空间之一**，不存在会话级绑定（P3-F03）。
2. 插件侧 `resolveKnowledgeForSpace()` 按「会话所在空间」解析可用知识库：项目空间绑定 + 所属部门绑定（部门级知识库在该部门的所有项目空间生效），返回按权重排序的绑定列表（P3-F04）。
3. 绑定关系不再依赖猜测：`ResolvedKnowledgeBinding.scopeId` 可直接作为 T-062 `retrieveForSpace({ allowedSpaceIds })` 的允许集，形成「绑定 → 允许集 → 检索过滤」的闭环。
4. 绑定与配置变更全部写审计：`kb.create` / `kb.update` / `kb.bind` / `kb.unbind`（§6.2 第 5 类「知识库配置和绑定变更」）。
5. `KnowledgeBinding` 增列 `weight`（迁移 `0003`），为「一个空间多知识库」提供确定性排序；迁移对「全新库」与「已升级 0002 的老库」都幂等。
6. 裁决：一个空间多知识库 **全部生效，按 `weight` 降序、`bindingId` 升序**排序 — 理由是需求要求「全部生效」且没有指定顺序字段，确定性排序才能让检索结果可复现 — 错判代价：管理员若期望别的排序口径，需要调整权重或后续引入显式优先级字段。
7. 裁决：部门级绑定**继承到该部门的项目空间** — 理由是部门是本部门项目空间的父范围，否则部门级绑定几乎无法生效 — 错判代价：若产品要求「部门绑定只在部门会话生效」，需去掉继承并在 `resolveKnowledgeForSpace` 收敛范围。
8. 裁决：控制面把知识库写操作收敛到**至少 admin** — 理由是 P3-F09 明确「管理员可配置 Provider、绑定空间、启停知识库」，而冻结矩阵把 `kb.bind` 也授予 member — 错判代价：member 无法自助绑定，需管理员执行；矩阵本身不变更，故该收敛点已在此登记供后续评审。
