# 知识库连接配置与健康检查（T-061）

## 1. 结论先行

1. `plugins/knowledge` 以官方插件形态建立：`package.json` + `plugin.manifest.json` + `dsh.bundle.patch`，不新增第二套插件装载器。
2. 通用 `http-rag` Provider（`src/providers/http-rag.ts`）实现契约⑨四项能力中的健康检查与配置校验，并提供检索实现供 T-062/T-063 复用。
3. 连接配置含**地址 / Token / 超时 / 默认参数 / 路径**，全部来自配置；Token 只接受「官方凭据服务已解析的事实」或一次性 `resolveToken()` 端口，本模块不落盘、不缓存（T-025 凭据边界同源）。
4. 四态健康检查可区分：`healthy`（200 且自报健康）、`unreachable`（连接失败/超时）、`auth_failed`（401/403 或凭据解析失败）、`sync_failed`（可达但 5xx/非 JSON/自报同步异常）。
5. 失败一律降级：`healthCheck` 返回状态而不抛错，`retrieve` 返回空数组，不向官方会话主链路抛未捕获异常（总览 §2.1 第 16 条、需求书 §5.4 第 3 条）。
6. 裁决：`spaceIds` 只上报**最具体**的空间范围（项目空间 → 部门 → 组织）——理由是绑定关系可反查、避免把组织级 ID 当作空间级授权；**错判代价**是若第三方 RAG 需要组织级过滤，需在 T-063 绑定解析处补一层映射。
7. 裁决：管理页面写入口取「至少 `admin`」与 `kb.bind` 的**交集**——理由是 P3-F09 明确「管理员可配置 Provider、绑定空间、启停知识库」，而冻结矩阵把 `kb.bind` 也授予 member（用于空间内自助请求）；**错判代价**是 member 在页面上看不到写入口，需走管理页面以外的方式发起绑定请求（不影响服务端裁决）。
