## 1. 结论先行

1. **打包与签名机制全部复用官方**：入口为 `pnpm run package:win:x64`（未签名测试用 `--unsigned`），签名走官方 electron-builder hook → 官方 `scripts/windows-sign.cmd` → SafeNet SignTool。**我方不新写打包器、不新写签名器。**
2. **签名输入是我的差异集**：只需在企业构建环境填 `.env.windows` 的 4 个 `DSH_DESKTOP_WINDOWS_*` 字段（证书、SignTool、私钥容器、Token PIN）；**算法、时间戳、缓存、互锁全部沿用官方**。
3. **更新源形态沿用官方双 origin 机制**：`DSH_DESKTOP_AUTO_UPDATE_ENV=test|production` 选择 `DSH_DESKTOP_MANDATORY_UPDATE_TEST_ORIGIN` 或 `..._PROD_ORIGIN`；**通道 = origin**，不新增机制。
4. **本阶段按裁决使用测试/自签证书 + 本地静态 HTTP 更新源**（总览 §2.1 第 6、7 条），并把「替换为正式证书 + 正式更新域名」登记为交付前待办。
5. **演练可以直接跑官方自带命令**：`node apps/desktop/node_modules/pnpm/bin/pnpm.mjs --dir apps/desktop run test:updates:local`，T-022 直接复用。
6. **未验证**：官方更新清单（feed）在下载域的实际路径。README 未给出 URL 形状；此前核查 `dsh-desk/bin/win-x64/latest.yml` 与 `latest.json` **均为 404**（研究文档记载），实际路径需在 T-022 的真实客户端请求中取证。

## 3. 逐项判定表

### 3.1 签名与打包方案

| # | 项 | 方案 | 依据（上游原文要点） |
| --- | --- | --- | --- |
| P-1 | 打包入口 | `pnpm run package:win:x64` | README：「Every package command builds the repository, packs the first-party production closures rooted at dsh and the private Desktop Host…」 |
| P-2 | 未签名测试包 | `pnpm run package:win:x64:unsigned` | README：「`--unsigned` modes do not run this hardware preflight; unsigned artifacts remain ineligible for release upload.」 |
| P-3 | 目录产物（免安装） | `pnpm run package:win:x64:dir` | README：「Create a runnable application directory instead of an installer by using the matching `:dir` command」 |
| P-4 | 证书字段 | `DSH_DESKTOP_WINDOWS_CER_FILE`（公开 EV 叶证书）、`DSH_DESKTOP_WINDOWS_SIGNTOOL`、`DSH_DESKTOP_WINDOWS_KEY_CONTAINER`、`DSH_DESKTOP_WINDOWS_TOKEN_PIN` | README：「Fill in `.env.windows` with …」 |
| P-5 | 签名实现 | 官方 CRLF `scripts/windows-sign.cmd` 调 SignTool，SHA-256 摘要，**不带时间戳**；随后 DigiCert RFC 3161 时间戳在隔离副本上完成 | README 原文 |
| P-6 | 预检 | 签名构建先跑 supervised signing preflight（静态配置、证书有效期、审计存储、编译器、互锁），60 秒截止 | README 原文 |
| P-7 | 签名不重试 | 「never retries a failed signing request」；`No private key is available.` = PIN 错误，**立即停止，不得重试**（5 次错误锁 token） | README 原文 |
| P-8 | 更新者身份 | `publisherName` 从证书 `CN`/`O`/`C` 派生，写入 `app-update.yml`；**下载到的 feed 不能决定它** | README 原文 |
| P-9 | 缓存 | `%USERPROFILE%\.dsh-desktop-signing\signature-cache\v1`（可用 `DSH_DESKTOP_WINDOWS_SIGNATURE_CACHE_DIR` 覆盖，须固定本地盘、属当前账户） | README 原文 |
| P-10 | blockmap | Windows NSIS 上传必须带非空 `.exe.blockmap`，先传 blockmap 再传 channel YAML | README 原文 |

### 3.2 证书选择（DG-12）

| 选项 | 是否可用 | 说明 | 本阶段处置 |
| --- | --- | --- | --- |
| EV 代码签名证书（USB token / SafeNet） | **上游设计目标** | 官方链路围绕 SafeNet token + SignTool `/kc` 设计；`publisherName` 从证书派生 | **未就绪**，登记为交付前待办 |
| OV 证书 | 可用（同上链路） | 无 EV 的硬件互锁语义差异，但机制一致 | 备选 |
| **测试 / 自签证书** | **本阶段采用** | 遵循总览 §2.1 第 6 条：用测试/自签证书完成升级与回退演练，演练记录必须写明证书类型 | **采用**；`--unsigned` 仅用于不自证签名的构建 |

**用途边界（必须写进演练记录）**：

- 自签/测试证书产物：**只能用于本机演练**，不得对外分发、不得作为交付物。
- `--unsigned` 产物：**不具备更新资格**（README 原文「unsigned artifacts remain ineligible for release upload」），仅用于构建验证。
- 正式产物：必须由企业 EV/OV 证书签名并完成时间戳。

### 3.4 升级 / 回退演练步骤（T-022 直接执行）

> 目标：构建 v0.1.0 → 发布到企业更新源 → 客户端检查更新 → 下载安装 → 重启后版本变 0.1.1。
> 本机演练用**官方自带本地演练**替代真实安装包链路（不写盘、不执行安装）：

```
Step 1  准备企业更新源（本地静态 HTTP 服务，绑定 127.0.0.1，随机端口）
Step 2  node apps/desktop/node_modules/pnpm/bin/pnpm.mjs --dir apps/desktop run test:updates:local
        断言（上游原文）：用户授权的全量下载 / SHA-512 拒绝 / 显式重试 /
                          并发请求合并 / feed 替换 / 安装交接
        成功标志：stdout 打印 LOCAL_UPDATER_RESULT，退出码 0
        证据留存：.desktop-build/qualification/local-updater-*（含截图，截图失败单独记录）
Step 3  真实安装链路演练（待证书与更新域名就绪后执行）：
        package:win:x64（企业证书） → 上传 installexe + .exe.blockmap + channel YAML
        → 客户端「Check for Updates」→ 下载 → 安装 → 重启后版本比对
Step 4  回退演练：把更新源切回上一版本 feed，重复 Step 3，确认可回退到 dsh-v0.1.7-rc.2 基线
```

**演练记录必须写明**：证书类型（自签/测试/正式）、更新源形态（本地静态/正式域名）、是否含真实安装。

## 5. 未验证项与边界

**需真机复核（B 类）**

- B-1：Windows 安装包实际安装/升级/卸载行为（含卸载对 `$DSH_HOME` 的保护）。
- B-2：`publisherName` 从自签证书派生后的实际匹配行为（正式证书到位后必测）。
- B-3：签名预检 60 秒截止在本机（无硬件 token）下的失败模式。

**需外部输入（C 类）**

- C-1：**官方更新 feed 的真实路径与格式**。缺什么：可观测的客户端更新请求（或官方说明）。怎么补：T-022 在本地演练中抓取客户端实际请求 URL；或向官方渠道确认。影响哪条验收：§4.1.5 关于「更新与回退可用」的条目。
- C-2：**企业 EV 代码签名证书**与 **USB token**。缺什么：证书文件、SignTool 路径、私钥容器、PIN。怎么补：由决策人采购/提供。影响哪条验收：§4.1.5 第 7 条（签名与更新）。
- C-3：**正式更新源域名与 CDN**。缺什么：域名、证书、发布权限。怎么补：由决策人决策。影响哪条验收：§4.1.5 第 7 条。
- C-4：上传通道凭据（README 提到 COS 相关脚本 `installed-update-cos.ts`、`cos-operation.ts`）——若采用对象存储需凭据；若改用内网 HTTP 则不需要。

**超出本次范围**

- O-1：不购买/不申请证书（安全敏感 + 外部采购）。
- O-2：不发布任何制品（总览 §6.4 第 3 类停止条件）。
- O-3：不做 macOS 签名与公证方案（需求书首选平台为 Windows）。
