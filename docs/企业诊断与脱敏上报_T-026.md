## 1. 结论先行

1. **§7.1 的字段白名单被逐字实现**：`DIAGNOSTIC_ALLOWED_FIELDS` 恰为需求书列出的 **9 项**（运行版本 / 平台与架构 / profile 校验结果 / 插件清单与状态 / 错误类型 / 错误码 / 脱敏后的错误摘要 / 时间戳 / 匿名安装标识），门禁断言其长度与内容。
2. **白名单外字段被「拒绝并列出」，不是静默丢弃**：`buildDiagnosticReport()` 返回 `rejectedFields`，便于本地查看与审计（门禁 D4：`prompt` / `title` / `apiKey` 被拒）。
3. **默认关闭，个人模式永不发送**：`isDiagnosticsEnabled()` 要求 `mode === 'enterprise'` **且** `adminEnabled === true`；个人模式即使控制面把开关置为 true 也不发送（需求书 §7.1 第 1 条）。
4. **P1 不发送任何数据**：三条不发送路径都被明确区分——`personal-mode` / `disabled` / `control-plane-not-connected`。**发送端在 T-054 接通**（门禁 D5 实测三条路径）。
5. **脱敏规则与 §4.2.4 同一套**：`Bearer`、`sk-*`、验证码（6 位数字**仅在验证码语境下**替换，避免误伤版本号）、已知密钥原值；官方 stderr **只保留头部并标注被截断的插件输出长度**。
6. **不重写官方诊断**：本模块是企业侧独立实现，**零引用** `crash-report` / `fatal-recovery` / `electron` / `ipcRenderer` / `node:fs`（门禁 D6），因此不构成第二套诊断体系（§11.14）。
7. **留存期约束已实现**：默认 30 天、上限 180 天（`clampRetentionDays`）。

## 5. 裁决记录

| # | 裁决：<决定> — <理由> — <错判代价> |
| --- | --- |
| R-1 | P1 只实现「可开关 + 可本地查看 + 不发送」，发送端留到 T-054——T-026 派发卡增补 S3 明确此裁决；P1 没有企业控制面——若在 P1 造一个发送通道，会形成第二套上报体系（§11.14） |
| R-2 | 白名单外字段**返回 `rejectedFields` 而不静默丢弃**——需求书要求「未列出的数据不得上报」，但本地查看与审计需要知道被拒了什么——若静默丢弃，出现越界字段时无人察觉 |
| R-3 | 验证码只在**验证码语境**下替换 6 位数字——无差别替换会误伤版本号、构建号、时间戳等合法信息，反而降低诊断价值——若误伤，诊断报告的可读性下降（错判代价低，但影响排查效率） |
| R-4 | 已知密钥原值替换**优先于**前缀规则，且按长度降序——短密钥可能是长密钥的前缀，顺序错会导致部分残留——若残留，等于把密钥写进报告（严重） |
| R-5 | stderr 只保留头部并标注截断长度——§7.1 明确要求「截断官方 stderr 尾部中的插件输出」；同时 stderr 原文**不进入**白名单字段，只能通过脱敏片段体现——若把 stderr 原文放进报告，直接违反禁止上报字段 |
| R-6 | 检测用正则**不带 `g` 标志**——带 `g` 时 `RegExp.test` 推进 `lastIndex`，同一正则在连续调用间结果不一致（本次单测实际捕获到该缺陷，已修正）——若不修，验证码脱敏会随机失效 |
