## 1. 结论先行

1. **差异集的唯一判定入口是本文 §3 的白名单表**。改动落在「上游文件」且不在白名单路径内，一律判为**白名单外**，走评审；不改上游文件的改动默认合法。
2. **白名单穷举为 5 类、共 14 条可检出条目**，每条含「路径模式 + 判定规则 + 责任人动作」，可直接被 T-027 的同步门禁脚本机器化检出。
3. **禁止差异清单对应需求书 §11 第 11~15 条**，核心是「不得改动官方核心行为」与「不得引入第二套机制」。
4. **同步节奏**：上游每发布一个正式版本，**≤5 个工作日**内完成一次 rebase 演练；差异新增需**决策人批准**并登记，不得静默分叉。
5. **冲突退让顺序固定**：以官方为准 → 需求打折 → 登记到需求书 §13.3。
6. **日落跟随清单**：上游废弃的模块/行为必须在我方同步时移除依赖；当前基线为首次锁定，清单为空集，规则先行。

## 5. 日落跟随清单（规则 + 现状）

**规则**：上游废弃某个模块、导出、配置键或行为时，我方必须在**同一轮同步**内：

1. 移除我方对该废弃项的**依赖引用**（代码引用、配置键、脚本参数）；
2. 在 `docs/差异集清单.md` 标注该差异条目为「随上游日落」并注明替代路径；
3. 若我方差异**只能**依赖该废弃项实现，则该差异必须重新评审（结论通常是「随上游砍掉」）。

**现状**：基线 `dsh-v0.2.0-rc.1` 为首次锁定，**已识别日落项为空集**。本规则先行，供 T-027 同步门禁逐轮执行。

## 6. 行为变化评审流程

上游新版本带来的**行为变化不自动成为我方基线**：

1. **发现**：T-027 同步门禁输出「上游行为变化候选清单」（含文件、导出、配置键、README 变更段落）。
2. **取证**：对每条候选，记录上游原文与本地影响面。
3. **评审**：判定为「跟随 / 不跟随 / 需改需求」三类之一。
4. **登记**：
   - 跟随 → 更新 `docs/差异集清单.md` 与基线版本号；
   - 不跟随 → 该差异必须落在 §3 白名单内，否则不得保留；
   - 需改需求 → 登记需求书 §13.3（让位）/ §13.4（修订映射）与 `内部准入评审记录` 决策变更区。
5. **责任人动作与位置**：评审结论由**执行代理**写入 `内部准入评审记录`「决策变更」区；需求变更由**决策人**批准后回写需求书。
