# 挂接官方插件管理器（T-100）

## 1. 结论先行

1. `plugins/market` 以官方插件形态交付（`type: composite`），企业侧只做**治理接入 + 市场入口声明**，不重复实现插件市场、不替换官方插件管理器。
2. **Step 0 / S2 取证结论（本次实测，来源 `packages/boot/plugin-manager` README 原文）**：
   - 官方包 `@deepseek-ai/dsh-plugin-manager`，Web 侧边栏「插件」页（`ui-plugin-manager`）负责浏览/安装/启停/卸载；
   - **安装输入形态**：`installBundle(spec)` 的 spec 支持「注册表包名 / 绝对路径 / git 地址 / tarball」四类；
   - **私有源**：`options.registry` → 配置的 `registry` → `fallbackRegistries` 依次询问；**配置集合之外的注册表只问它自己**，因此私有源不会落到公共源；
   - 事件：`plugin-manager/changed`、`install-log`、`install-state`；其他能力：`listBundles`、`inspect`、`waitForInstall`、`cancelInstall`；
   - **官方未提供审批弹窗**：`plugin_manager` 工具要求 `danger-full-access` 或单次批准 → 企业审批必须在企业控制面/企业 UI 完成（§4.6.2）。
3. `src/official-manager.ts` 把官方能力面包装为**可注入端口**（`OfficialPluginManagerPort`），企业侧只在安装前后做白名单/审批/锁定判断，不改官方流程。
4. 治理复用 T-032 的 `createGovernanceHooks` / `attachGovernanceHooks`：非白名单安装返回 `deny` 并写审计，启停/卸载只记录（不接管生命周期）。
5. 裁决：安装输入形态采用**官方四类 spec 原样透传**，企业侧不解析也不改写 spec — 理由是官方已用 `pnpm view` + 注册表计划完成校验与私有源隔离 — 错判代价：若企业需要额外校验（例如只允许私有源），必须在 T-102 的白名单/来源校验里补，而不是在这里改 spec。
6. 裁决：市场入口以页面声明 + 只读 `describeMarket()` 暴露，真实浏览器/安装动作仍由官方管理器执行 — 错判代价：企业 UI 的审批交互需在 T-102/T-104 补足。

## 4. 未验证项与边界

**需真机复核（B 类）**

- B-1：真机确认官方插件管理器的浏览/安装/启停仍可用（企业侧未改变官方行为）。
- B-2：企业审批弹窗在企业 UI 内的呈现（官方无审批对话框）。
- B-3：私有源在真实 profile 中的注册表计划与凭据注入。

**需外部输入（C 类）**

- C-1：企业私有 registry 地址与凭据（T-101 用本地桩推进）。
- C-2：企业白名单与审批人名单。

**超出本次范围**

- O-1：不自研插件市场、不替换官方管理器、不引入 `dshmarket`（§1 决策 11、§4.6.2 约束）。
- O-2：不新增插件管理 IPC、不改官方安装/启停/卸载流程。
