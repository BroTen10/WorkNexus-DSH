# 插件版本锁定与兼容性检查（T-103）

## 1. 结论先行

1. `services/api/app/services/plugin_policy.py` 提供纯函数策略面：semver 比较（含 prerelease）、范围校验、声明必填校验、兼容性判定、锁定判定（P6B-F04/F05、§5.5）。
2. 白名单写入时**强制声明** `dshCompatibility` 与 `hostCoreCompatibility`：缺失返回 422 `invalid_compatibility_declaration`，两份问题列表点名缺哪一项（对上游 T-102 阶段留空的条目形成闭环）。
3. 范围不匹配（例如声明 `>=0.3.0 <0.4.0` 而锁定 DSH 为 `0.2.0-rc.1`）返回 422 `incompatible` 并给出逐条原因。
4. 版本锁定：`POST /market/plugins/{id}/lock` 锁定白名单版本；锁定后 `POST /market/plugins/{id}/upgrade` 返回 409 `version_locked`（**不自动升级**），写 `market.version.lock` 审计。
5. semver 规则与上游一致：`0.2.0-rc.1 < 0.2.0`、`0.2.0-rc.2 > 0.2.0-rc.1`；契约版本独立演进，`CONTRACT_VERSION` 与 `packages/contracts/src/version.ts` 同源（门禁断言相等）。
6. 裁决：兼容性判定在**控制面**（权威），客户端声明校验沿用 `plugin-runtime` 的 `checkCompatibility`（T-031）— 理由是两端各有职责：客户端做安装前预检，控制面做治理裁决 — 错判代价：两处规则漂移会导致「预检通过但治理拒绝」，故门禁同时校验两侧常量一致。
7. 裁决：锁定的粒度是「插件 + 锁定版本」而非版本区间 — 依据 T-103 派发卡默认裁决（按插件 + 版本范围审批）在锁定时退化为单一版本更易审计 — 错判代价：需要区间锁定时要扩展 `locked_version` 语义。
