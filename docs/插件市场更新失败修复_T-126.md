# 插件市场更新失败修复（T-126）

## 1. 结论先行

2026-10-18 真机「更新已安装插件失败」不是网络或插件包本身的问题，而是两个独立缺陷叠加：

1. **市场侧**：随包 `dshmarket@1.66.9` 仍把「更新」映射成官方 `installBundle(spec)`。DSH 0.2.1（alpha.2/rc.2）在 HMR 开启时对已安装包**在跑 pnpm 之前**就以 `already-installed` 拒绝（`packages/boot/plugin-manager/src/index.ts:542-545`），所以任何已安装插件都更新不了。`dshmarket@1.66.37` 已按上游 #896/#897 改为「先 `removeBundle` 再 install」。
2. **企业层**：`backfilledPresetDependencies()` 会把 profile 里任何「精确版本且与随包版本不同」的预置插件依赖改回随包版本。市场 2026-10-15 把 `dsh-claude-style` 更新到 0.14.0 后，下一次启动被改回 0.13.2、`node_modules` 也被物化回 0.13.2，但 `pnpm-lock.yaml` 仍记 0.14.0。于是本次更新失败后的回滚校验看到「磁盘 0.13.2 / 锁文件 0.14.0」，拒绝自动回滚并显示红字。

修复：跟版 `dshmarket` 到 1.66.37（连带 `undici` 7.29.1），并把启动补齐改为**只向前同步**（低于随包版本才前进，等于/高于一律保留）。代码、差异集与门禁已完成；安装包已重建并装机，**当前客户端已是修复构建**。

> 后续：2026-10-19 已按同一 vendor 流程跟到 **1.66.42**，继续保持本修复并纳入 release-age 假回滚、宿主重启归属、profile 锁恢复与 carrier 安装树判定；见 [`插件市场跟版_1.66.42_T-144.md`](插件市场跟版_1.66.42_T-144.md)。

### 裁决

- **跟版 `dshmarket` 到 1.66.37，而不是自行 patch 1.66.9** — 上游已针对本问题给出完整修法（#896/#897），自维护分支会把后续跟版成本放大 — 错判代价：1.66.10~1.66.37 的其它 UI/行为变化随之进入发行版。
- **保留向前的版本同步，只取消向后回退** — 维持「发行版升级时预置插件版本锚点跟着走」的原意，同时保证市场装上的新版不被覆盖 — 错判代价：若市场装了低于随包版本的精确版本（市场本身禁止降级），下次启动会被拉回随包版本。
- **本轮不重出包** — 沿用「修复攒批、最终一次打包」的既有约定 — 错判代价：在重出包前，已安装客户端仍会复现该失败。

## 4. 未验证项与边界

- **已闭环（B 类）**：决策人在修复构建上实测更新，回执「测试通过」；`already-installed` 与版本回退问题不再复现。
- **需真机复核（B 类）**：当前 profile 的 lockfile 漂移（package.json 0.13.2 / lock 0.14.0）会在第一次成功的市场更新时由 pnpm 重写；在此之前 profile 仍处于该不一致状态，但新市场不再依赖它做回滚。
- **需外部输入（C 类）**：目标版本（claude-style 0.16.2、better-sidebar 0.28.0、skill-explorer 0.4.7）与 rc.2 的兼容性由市场自身的 compatibility check 判定，本轮未逐版本验证。
- **既有边界**：发行版把预置插件版本向前推进时，启动补齐仍只改 `package.json` 与 `node_modules`，`pnpm-lock.yaml` 会落后一版，直到下一次成功的市场操作由 pnpm 重写；本轮没有在启动路径里改写锁文件（缺少可靠的 integrity 来源，贸然重写风险更高）。
- **超出本次范围**：GUI 目视与真实 profile 的插件更新点击；出包、安装与装机态门禁已完成。
- **边界**：`dshmarket` 自身未来再升级仍按 vendor 锁文件流程跟版；本次没有改动上游 plugin-manager 的 `already-installed` 语义。
