## 1. 结论摘要

WorkNexus-DSH 以 **DeepSeek Harness / DSH 官方开源桌面端为客户端基线**，在上面叠加**业务侧个性化**（企业管理、知识库、DocGraph Adapter、IPD Demo、企业插件治理），并以**不可拆卸的 Host Core** 承载企业横切契约。

平台按「阶段插件」推进：每一阶段尽量形成可独立安装、禁用、卸载的业务插件；某个新插件失败时，不得影响已有内核、客户端、企业管理插件或知识库插件的运行。

关键决策如下：

1. **DSH 是执行内核，官方 DSH Desktop 是客户端基线**。WorkNexus-DSH 负责企业发行版、控制面、插件治理和业务集成，**不重写客户端壳、进程管理、更新器、诊断、插件加载器**。
2. **基础功能侧严格遵循官方设计**。凡本说明书与官方开源实现冲突之处，**以官方设计为准**，本说明书需求让位，并在 §13.3 登记让位原因。此处的「官方」指 **§3.4 锁定的上游发行版 tag 所定义的既定行为与设计文档**；上游升级后行为发生变化**不自动改变本基线**，必须先经差异集评审，再同步更新本说明书（见 §3.4、P1-F15）。
3. **个性化只体现在业务侧**。允许的差异仅限：产品品牌与文案、企业更新源与签名、随发行版预置的第一方 bundle 清单、企业侧页面入口。差异必须可枚举、可审计、可 rebase。
4. DSH Web profile 是交互主链路；ACP 只作为后台自动化能力，不在第一阶段替换主交互链路。
5. 增加**不可拆卸的 Host Core**。它不是业务插件，负责身份、空间、权限、审计、Token/用量、事件、插件注册、升级恢复等横切契约；落地形态为**随发行版预置的内置 bundle**（不得依赖外部插件安装）。
6. 企业管理界面做成可拆卸插件，但其中的身份、空间、权限、审计、用量契约必须沉淀在 Host Core。
7. 知识库按**部门空间或项目空间**绑定，不以会话级绑定为主。
8. DocGraph 第一版以**独立服务 + 轻量 Adapter 插件**接入，不做深度拆分改造。
9. IPD 插件优先级最低，第一阶段只做入口和 Demo 展示，不承诺真实流程引擎。
10. 初期注册方式采用**邮箱 + 验证码**，SSO 延后。
11. 插件治理**复用官方插件管理器**（`dsh-plugin-manager` + Web 侧栏 Plugins 入口），企业侧只补私有源、白名单、审批和治理；`dshmarket` 降级为第三方生态参考。
12. 总原则是**成熟度优先、可用性优先、上游客随度优先、需求可打折**，避免过早抽象和复杂拆分。

## 2. 产品定位

### 2.1 产品形态

WorkNexus-DSH 是一个面向个人到企业场景的 AI 工作平台。

产品由四类部分组成：

| 层 | 说明 | 责任方 |
| --- | --- | --- |
| Desktop Shell | Electron 客户端壳，负责窗口、启动、更新、进程守护、本地设置和 UI 容器 | **官方 DSH Desktop（我方仅做品牌与发行定制）** |
| DSH Runtime | DSH 内核，使用 Web profile 承载 Agent 会话，内置独立 Node/pnpm/Python 运行时 | **官方** |
| Host Core | 平台宿主契约层，不可拆卸，承载横切能力 | **我方**，以预置内置 bundle 形式交付 |
| Business Plugins | 企业管理、知识库、DocGraph Adapter、IPD Demo 等可拆卸业务插件 | **我方** |

【v1.1 变更】v1.0 将 Desktop Shell 与 DSH Runtime 全部列为 WorkNexus-DSH 自研范围；v1.1 改为官方提供，我方只做发行定制。

### 2.2 首选平台

- 第一版以 **Windows 桌面客户端**为主，与官方桌面端首发平台一致。
- 官方同时提供 Apple 芯片 macOS 构建；我方第一版不承诺 macOS/Linux 发行，后续按需评估。

### 2.3 目标用户

| 角色 | 目标 |
| --- | --- |
| 个人用户 | 快速启动 DSH 会话、管理历史、恢复上下文 |
| 企业管理员 | 管理组织、部门、项目空间、成员、权限、审计和用量 |
| 团队负责人 | 管理部门或项目空间内的成员、知识库和协作内容 |
| 普通成员 | 在授权空间内使用 Agent、知识库、文档和业务插件 |
| 只读用户 | 查看授权范围内的项目、文档、结果和统计信息 |

## 3. 总体架构边界

### 3.1 官方基线、DSH 与 WorkNexus-DSH 的边界

**官方 DSH Desktop 负责（我方不改，仅跟随）：**

- 桌面客户端壳与窗口/托盘/关机行为；
- 内置 dsh runtime、Node/pnpm/Python 运行环境；
- profile 初始化、单实例锁、`$DSH_HOME/profiles/desktop` 所有权；
- 自动更新、强制更新策略、签名与发行通道；
- 崩溃恢复、诊断、崩溃报告；
- 插件管理器（安装/启用/禁用/卸载外部 bundle）与 Web 侧栏 Plugins 入口；
- Agent 会话执行、模型调用、工具调用、profile/plugin 组合、Web 会话界面；
- SDK / ACP 等程序化接入能力。

**DSH 负责：**

- Agent 会话执行、模型调用、工具调用、profile / plugin 组合、Web 基础能力、SDK / ACP 接入。

**WorkNexus-DSH 负责：**

- 企业发行版：品牌、发行渠道、企业更新源与签名、预置 bundle 清单；
- 企业组织、空间、成员和权限；
- 操作审计与 Token 用量、预算；
- 知识库接入与权限过滤；
- DocGraph、IPD 等业务插件；
- 企业插件治理与私有源；
- 上游版本锁定、跟随与兼容性策略。

**WorkNexus-DSH 不负责（v1.1 明确）：** 不重新实现 DSH 的 Agent 执行内核、工具调用内核和插件加载内核；**也不重新实现官方桌面壳、进程管理、更新器、崩溃恢复、诊断导出、会话界面**。

【v1.1 变更】v1.0 把「桌面客户端体验、自动更新与升级恢复」列为我方职责，v1.1 移除该职责并划归官方基线。

### 3.2 Host Core 的定位

Host Core 是 WorkNexus-DSH 的宿主契约层，不是业务插件。

它至少包含以下契约：

| 契约 | 最小职责 |
| --- | --- |
| IdentityContext | 当前用户、登录态、邮箱、组织归属 |
| SpaceContext | 当前组织、部门、项目空间 |
| PermissionPolicy | 判断用户是否可执行某资源上的某操作 |
| AuditSink | 写入操作审计事件 |
| UsageLedger | 记录 Token、模型、会话、用户、空间、成本等用量 |
| EventBus | 企业事件通道：企业事件命名空间 + 订阅白名单；**复用官方事件机制，不替换官方通道** |
| PluginGovernanceView | 只读镜像官方插件状态；白名单 / 审批判定；插件事件转企业审计；**官方 plugin manager 是启停的唯一权威** |
| UpdateManager | 发行版版本锁定口径、上游跟随策略、差异集状态与 rebase 演练记录；**更新与回滚由官方实现** |

与 DSH 的关系结论：**不冲突**。

DSH 的「一切皆插件」主要指 Agent / profile / 业务能力可以通过插件组合。WorkNexus-DSH 的 Host Core 属于企业平台宿主层的横切契约，不是替代官方 plugin manager 的第二套插件系统。如果某部分 Host Core 能力需要进入 DSH profile，应标记为 `host-infrastructure` 或 `protected`，禁止普通用户禁用。

【v1.1 新增落地约束】Host Core **必须随发行版预置在 profile 的内置 bundle 段**，不能依赖用户安装外部插件；原因是官方原生恢复动作允许「禁用第三方 bundle」，而需求要求 Host Core 不可拆卸。

### 3.3 控制面技术基线

企业模式下控制面建议采用：

- FastAPI；
- PostgreSQL；
- 标准化 REST API；
- Alembic 迁移；
- JWT 或短期 Access Token + Refresh Token；
- 操作审计表；
- 用量与预算表。

【v1.2 修订】是否需要部署控制面由**运行模式**决定（见 §3.5）：个人模式不要求部署完整企业控制面，可以使用本地配置与 DSH 自身能力；企业模式必须使用控制面持久化组织、成员、权限、审计和用量。

【v1.1 新增】企业控制面与官方 `packages/api`（api-gateway）边界：官方 api-gateway 服务本地 Agent 会话；企业控制面只服务企业资源（组织/空间/权限/审计/用量/知识库绑定/外部服务），**不接管官方会话链路**。两者鉴权与凭据存储各自独立，企业控制面不得要求官方会话携带企业 Token。

### 3.4 上游基线与跟随策略

【v1.1 新增章节】

- **基线仓库**：`deepseek-ai/deepseek-harness`（MIT，Copyright (c) 2026 DeepSeek）。
- **锁定口径**：锁定**官方桌面发行版 tag**（首个基线为 `dsh-v0.2.0-rc.1`；**当前基线为 `dsh-v0.2.0-rc.2`**，2026-09-29 经决策人批准迁移，见 `内部基线迁移记录`），并接受官方既有规则——**Electron 壳与 `@deepseek-ai/dsh` 版本恒等**、**壳 + dsh runtime + pnpm 构成一个签名更新单元**。
- **允许的差异集（白名单，穷举）**：
  1. 产品品牌、产品名、图标、引导与关于页文案；
  2. 企业更新源、更新通道与签名证书；
  3. 随发行版预置的第一方 bundle 清单与 `protected` 标记；
  4. 企业侧页面入口挂载（企业管理、知识库、DocGraph、IPD）；
  5. 企业侧默认配置项（不含官方核心行为开关）。
- **禁止的差异**：修改官方核心行为（会话执行、工具调用、插件加载、更新算法、恢复策略、安全基线）；新增第二套插件系统、第二套凭据存储、第二套诊断体系。
- **同步节奏**：每个上游正式版本至少执行一次 rebase 演练；差异集与上游冲突必须在合并前解决，不允许长期分叉。**上游行为变化不自动成为本需求基线**——需先完成差异集评审，再同步更新本说明书。
- **命名合规**：沿用 `BRAND_GUIDELINES`——项目名使用缩写 **DSH**（WorkNexus-DSH 已符合），描述中使用「built on DeepSeek Harness / 兼容 DeepSeek Harness」，**不得在项目名中使用 "DeepSeek Harness" 全称商标**，不得使用官方品牌素材暗示官方背书。

### 3.5 运行模式

【v1.2 新增】本说明书用「个人模式」与「企业模式」区分是否接入企业控制面，判定与差异如下：

| 项 | 个人模式 | 企业模式 |
| --- | --- | --- |
| 判定条件 | 未登录企业账号，或已登录但未选定组织 | 已登录企业账号**且**已选定组织（具备组织上下文） |
| 默认值 | 首次启动默认个人模式 | 登录并选定组织后进入 |
| 官方能力 | 会话、工作区、模型、插件等官方能力全部可用 | 同左 |
| 企业控制面 | 不连接 | 必须连接（P2 起） |
| 插件治理 | 只记录可疑安装，不强制白名单 | 白名单与审批强制生效（§4.6.2 验收 2） |
| 数据归属 | 本地与个人用量 | 归属组织 / 空间，进入企业审计与用量 |
| 模式切换 | 登录并选定组织 → 企业模式；登出或清除组织上下文 → 个人模式 | 同左 |

规则：

1. 模式由**当前登录态与组织上下文**决定，不提供手工强制开关。
2. 两种模式在同一客户端共存；切换不回滚、不删除既有官方会话与工作区数据。
3. 退回个人模式时，企业侧数据不复制到本地；企业侧功能入口隐藏而不报错。
4. 企业模式不可用时（控制面不可达或组织上下文失效），客户端与 DSH 会话仍可用，企业侧功能降级并给出明确提示（对应 §5.4 失败隔离）。
5. P1 阶段只交付个人模式；企业模式自 P2 起启用。

### 4.2.3 角色与权限

基础角色采用四类，避免第一版做过细的权限编辑器：

| 角色 | 组织级能力 | 空间级能力 |
| --- | --- | --- |
| `owner` | 全部管理能力，包括删除组织、转移所有权、插件治理、审计、预算 | 默认拥有全部空间管理能力 |
| `admin` | 管理组织成员、部门、项目空间、插件启停、审计、预算，但不能删除组织或转移所有权 | 管理授权范围内的空间 |
| `member` | 加入授权空间，创建和操作自己的内容 | 创建会话、上传文档、使用授权插件 |
| `viewer` | 查看授权范围内的只读内容 | 查看文档、结果和统计，不触发产生 Token 的动作 |

规则：

1. 默认最小权限。
2. 用户必须在空间内显式授权。
3. 空间内可以授予 `admin`、`member`、`viewer`。
4. 组织级 `owner` 不需要逐个授权即可管理组织内资源，但操作必须审计。
5. 第一版不做自由组合的细粒度权限点编辑器。

### 4.2.4 审计与隐私

审计记录至少包括：

- 事件 ID；
- 时间；
- 用户 ID；
- 组织 ID；
- 空间 ID；
- 操作类型；
- 资源类型；
- 资源 ID；
- 结果；
- IP / 设备标识；
- 摘要。

默认规则：

- 不记录完整 prompt 和完整模型输出；
- 不记录 API Key、密码、验证码等敏感值；
- 摘要中只包含必要的资源名称或资源 ID；
- 管理员可查看元数据和统计，不能默认浏览所有会话正文；
- 后续如需会话内容治理，必须单独设计合规策略。
- 企业侧诊断上报遵循 §7.1（字段白名单、脱敏、留存与访问）。

**留存与不可篡改**

- 审计事件与用量记录**只追加、不原地修改**；纠正错误采用追加更正事件（记录原事件 ID），不得覆盖或删除原记录。
- 留存期：按合同与合规要求设定，第一版默认**不少于 3 年**；到期归档或清理必须经 `owner` 批准并写入审计。
- 删除权限：删除或清理仅限 `owner`，且必须记录操作人、范围、条数与原因。
- 检索与导出：`owner` / `admin` 可检索与导出元数据，导出行为本身写入审计。
- 会话正文不属于本体系（沿用本节「不记录完整 prompt 与模型输出」的默认规则）。

### 4.2.5 Token 预算

第一版预算策略：

1. 支持组织总预算。
2. 支持部门或项目空间预算。
3. 支持用户月度预算。
4. 支持软阈值提醒和硬阈值阻断。
5. 阻断策略必须清楚提示，不允许静默失败。

用量的数据来源优先使用 DSH 原生会话或运行时事件。如果 DSH 当前版本没有稳定事件，则在 WorkNexus-DSH Adapter 层汇总，但不得伪造数据；无法获得的字段必须显示为未知或估算值。

【v1.1 补充】可用来源按优先级：① 官方 session 投影（会话级 token/上下文压力）；② 官方账号用量能力（若可用）；③ 官方 telemetry。三者都不可得的字段保持空值。

### 4.2.6 Host Core 契约要求

P2 必须把以下能力沉淀为 Host Core 契约：

1. 身份上下文；
2. 空间上下文；
3. 权限判断；
4. 审计写入；
5. Token 用量写入；
6. 插件治理视图（只读镜像官方插件状态，官方是启停权威）；
7. 插件事件订阅（安装 / 启用 / 禁用 / 卸载事件转企业审计）；
8. 插件权限声明（企业权限点校验）。

企业管理插件可以卸载，但这些契约不能随插件一起消失。

【v1.1 补充】契约落地形态：随发行版预置的内置 bundle；插件注册与启停**挂接官方插件管理器的事件**，不另建注册表实现。治理视图不提供 enable / disable 语义。

### 4.2.7 验收标准

1. 用户可通过邮箱验证码完成注册、登录。
2. `owner` 可创建组织、创建部门、创建项目空间、邀请成员并授权。
3. 未授权空间对普通成员不可见。
4. 四类角色在授权空间内表现符合权限矩阵。
5. 关键操作可生成审计记录，管理员可按用户、时间、操作类型查询。
6. Token 用量能按用户、空间、模型统计。
7. 超过硬阈值后，可阻止新的会话或提示提交，并给出明确提示。
8. 卸载或禁用企业管理 UI 后，客户端和 DSH 会话仍可运行。

【v1.1 新增】9. 企业插件安装/启停/卸载事件可在审计中查询。

## 4.6 P6：后续增强阶段

P6 拆分为三个子阶段，避免范围膨胀。

### 4.6.1 P6A：ACP 后台自动化

ACP 在 DSH 官方资料中是正式能力，定位为面向程序化客户端和维护者的自动化协议，支持创建、恢复、关闭会话，提交或取消工作，选择模型与推理强度，挂载 MCP，接收语义更新和权限请求。

但 ACP 不承载 DSH 专用交互 UI，因此只用于后台自动化。

功能要求：

1. 增加 `AcpTransport`，实现 §6.4 定义的 `AgentTransport` 契约（该契约在 v1.2 中只服务于 ACP 后台任务，**不由 P1 实现**）。
2. 支持后台任务创建、状态查询、取消、恢复和关闭。
3. 支持任务与用户、空间、插件关联。
4. 所有 ACP 权限请求必须有企业侧策略或管理员确认。
5. ACP 会话必须进入审计和用量体系。
6. ACP 不用于替换普通用户的交互会话。

【v1.1 补充】`AcpTransport` 的协议实现**复用官方 `packages/acp`**，我方只做企业侧适配（任务归属、权限策略、审计用量），不自研 JSON-RPC 传输层。官方明确列出 ACP 的能力边界：支持创建/恢复/关闭会话与取消工作，**不支持**删除、Fork、转录回放与额外目录。

验收标准：

1. 至少一个后台自动化任务可通过 ACP 完成。
2. 任务可从后台列表查看和取消。
3. 会话恢复、关闭、取消行为符合预期。
4. ACP 插件禁用后，P1 至 P5 功能不受影响。

### 4.6.2 P6B：插件市场与企业治理

【v1.1 改写】v1.0 写「不重复建设插件市场，优先复用 `dshmarket`」。v1.1 改为：**复用官方插件管理器**（`dsh-plugin-manager` + Web 侧栏 Plugins 入口，支持启停插件条目、选择已安装 bundle、安装/移除外部 bundle，使用内置 pnpm）；`dshmarket` 降级为第三方生态参考，不再是首选。

WorkNexus-DSH 增加企业治理能力：

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| P6B-F01 | 私有插件源 | 支持企业私有 registry 或镜像 |
| P6B-F02 | 插件白名单 | 只有通过审批的插件可安装 |
| P6B-F03 | 安装审批 | 企业管理员可审批插件安装、更新和启停 |
| P6B-F04 | 版本锁定 | 可锁定插件版本，避免自动更新引入风险 |
| P6B-F05 | 兼容性检查 | 插件必须声明 DSH 版本范围和 Host Core 契约版本 |
| P6B-F06 | 安全提示 | 显示插件权限、来源、风险和最近更新信息 |

【v1.1 新增约束】治理能力**挂接官方插件管理器的安装/启停/卸载事件**，不替换其实现；官方未提供审批弹窗（官方明确「依赖生命周期脚本遵循 pnpm 构建权限，桌面端不提供单独审批对话框」），企业审批必须在企业控制面或企业 UI 内实现，不改官方流程。

验收标准：

1. 官方插件管理器可在发行版中浏览和安装插件。
2. 企业模式下未通过白名单的插件不能安装。
3. 插件安装、更新、禁用有审计。
4. 私有源不可用时不影响已有客户端启动。

### 4.6.3 P6C：SSO 与深度治理

延后实施。

触发条件：

1. 企业客户明确要求对接统一身份系统；
2. 组织规模扩大到邮箱验证码管理不便；
3. 需要对接企业合规、数据防泄漏或集中日志平台。

候选能力：

1. OIDC / SAML / LDAP；
2. 细粒度权限策略；
3. 数据分级；
4. 会话内容治理；
5. 集中 SIEM 日志；
6. 企业密钥托管和模型网关。

## 5. 插件架构要求

### 5.1 插件类型

WorkNexus-DSH 插件包可包含以下一种或多种内容：

| 类型 | 说明 |
| --- | --- |
| UI Plugin | 注册到客户端界面的页面、菜单、卡片或操作 |
| DSH Plugin | 以 DSH profile / bundle 形式加入 Agent 能力 |
| Service Adapter | 连接外部服务，例如知识库或 DocGraph |
| Governance Plugin | 提供审批、私有源、治理或策略能力 |

第一版优先使用单一插件包描述，避免过早拆分。只有当某部分确实需要独立部署或独立生命周期时，才拆成服务或子包。

【v1.1 改写】**插件必须使用官方机制交付**：以官方 profile bundle / 插件声明方式注册与装载，遵循官方 plugin manager 的安装、启用、禁用、卸载行为。WorkNexus-DSH **不提供第二套插件装载器**。

### 5.2 企业插件声明

【v1.1 改写】v1.0 自行定义了一套插件 Manifest 最小字段集。v1.1 改为**在官方 bundle/插件声明之上附加企业治理字段**，不另立第二套规范。企业侧额外声明至少包含：

```yaml
id: string                      # 企业插件标识
name: string                    # 展示名
version: semver
type: ui | dsh | service | governance | composite
dshCompatibility: ">=x.y.z <a.b.c"          # 官方 DSH 版本范围
hostCoreCompatibility: ">=x.y.z"            # Host Core 契约版本
protected: boolean                          # true 时随发行版预置、禁止普通用户禁用
permissions:                                # 企业权限点（沿用 Host Core 枚举）
  - identity.read
  - space.read
  - audit.write
  - usage.write
  - kb.retrieve
uiSlots: []                                 # 官方 UI 槽位声明
governance:
  source: private-registry | official | local
  approval: required | none
```

语义必须保留；具体字段名可在技术设计阶段调整，但**不得与官方 bundle 声明冲突，也不得要求官方客户端理解企业字段**（企业字段只在企业侧读取）。

### 5.3 生命周期

插件必须支持：

1. 安装；
2. 启用；
3. 禁用；
4. 卸载；
5. 版本升级；
6. 回滚；
7. 健康检查；
8. 失败上报。

【v1.1 改写】上述生命周期**由官方 plugin manager 提供**；WorkNexus-DSH 的职责是**订阅其事件并补齐企业治理语义**（谁在什么空间安装了什么版本、是否通过白名单与审批、是否进入审计），而不是重新实现生命周期。

### 5.4 失败隔离

必须满足：

1. 插件启动失败不阻断 Host Core。
2. 插件 UI 渲染失败不阻断 DSH 会话。
3. 插件外部服务不可用时不阻塞主界面。
4. 禁用插件后，相关菜单、页面、Agent 工具和后台任务应停止注册。
5. 可选依赖缺失时，插件应降级运行或明确提示不可用，不能崩溃主程序。

6. 企业预置 bundle（Host Core 与业务插件基座）必须是**内置 bundle**，不得被官方原生恢复动作的「禁用第三方插件」路径误禁（对应 P1-F16 与 §4.1.5 第 8 条）。
   - **降级路径（需批准）**：若 P0 阶段 T-005 的可行性验证证明该要求在锁定上游版本上无法达成，必须先由决策人批准降级，并把 P1-F16 与 §4.1.5 第 8 条同步改写为「企业 bundle 被原生恢复禁用时，必须提供一次性恢复入口，且恢复过程不得丢失企业数据」。**未获批准前，本条第 1 句保持为硬要求**，验收按 §4.1.5 第 8 条判定。
   - 降级决定必须登记到 §13.4 与 `内部准入评审记录` 的决策变更区。

### 5.5 版本策略

1. 每阶段锁定 DSH 版本。
2. 插件 Manifest 声明兼容范围。
3. Host Core 契约版本独立于产品版本演进。
4. 升级 DSH 前必须运行基础兼容性检查。
5. 升级失败必须能回到最近可用客户端或 DSH profile 状态。

【v1.1 补充】6. 官方规则：**Electron 壳、dsh runtime、pnpm 构成一个签名更新单元**，壳与 `@deepseek-ai/dsh` 版本恒等；**DSH 升级即桌面发行版升级**，我方跟随方式为锁定并升级上游发行版 tag，不得单独升级壳或内核。
【v1.1 补充】7. 每个上游正式版本至少一次 rebase 演练，差异集冲突在合并前解决（见 P1-F15）。

| EmailVerificationCode | 邮箱验证码 |

### 6.2 审计事件

必须审计：

- 登录、注册、验证码请求；
- 组织、部门、空间创建和变更；
- 成员邀请、移除、角色变更；
- 插件安装、更新、启停、卸载；
- 知识库配置和绑定变更；
- DocGraph 任务提交、取消；
- Token 预算变更；
- 客户端版本升级。

### 6.3 用量事件

用量记录至少包括：

```yaml
usage_id: string
timestamp: datetime
organization_id: string
space_id: string | null
user_id: string
session_id: string | null
plugin_id: string | null
provider: string
model: string
prompt_tokens: int | null
completion_tokens: int | null
total_tokens: int | null
estimated_cost: number | null
source: dsh_event | adapter_estimate | manual_import
```

无法获得的字段必须保持空值，不允许填假数。

### 6.4 AgentTransport 最小接口

`AgentTransport` 是内部适配层，不做成过度抽象的协议网关。

最小能力：

```ts
interface AgentTransport {
  createSession(input): Promise<SessionHandle>
  resumeSession(sessionId): Promise<SessionHandle>
  sendMessage(input): AsyncIterable<AgentEvent>
  cancel(sessionId): Promise<void>
  closeSession(sessionId): Promise<void>
  listSessions(query): Promise<SessionSummary[]>
}
```

实现策略：

1. 【v1.2 修订】P1 **不实现本接口**：交互主链路的会话能力直接使用官方实现与官方已鉴权 HTTP API，不为已有官方能力再造一层封装。
2. 本接口在 v1.2 中**仅作为 ACP 适配的目标契约**（P6A），不要求 P1 存在实现。
3. 不在 P1 强制所有能力都通过统一接口抽象，只约束新增后台自动化时不推翻交互主链路。

【v1.1 补充】4. 本接口只服务于企业侧需要介入的场景（例如 ACP 后台任务、DocGraph 结果引用）；接口签名以官方实际能力为准，官方不支持的能力（删除、Fork、转录回放、额外目录）**不得在接口层伪装支持**。

| 类别 | 需求 |

| 兼容性 | 升级 DSH 或插件前必须做版本兼容检查 |
| **上游客随度** | 差异集白名单化、可枚举；每个上游正式版本至少一次 rebase 演练；不得长期分叉 |

## 10. 风险与处理策略

| 风险 | 影响 | 处理策略 |
| --- | --- | --- |
| DSH 版本快速演进 | 插件或客户端兼容性被破坏 | 每阶段锁定版本，升级前做兼容检查，保留回滚 |
| **上游桌面端仍处 rc/alpha** | 官方接口与行为可能变动 | 锁定具体 tag，不追 head；升级前跑 rebase 演练与冒烟 |
| **fork 分叉成本** | 差异集膨胀导致无法跟随上游 | 差异集白名单化 + 每次上游发版 rebase 演练；差异超限即回退到官方设计 |
| **企业 bundle 被原生恢复动作禁用** | Host Core 不可拆卸的承诺失效 | 预置为内置 bundle；把「原生恢复不误禁企业 bundle」作为验收项 |
| DSH Web 能力与平台 UI 需求不完全匹配 | 会话界面改造范围扩大 | P1 只做承载和增强，不重写 DSH UI |
| Token 用量字段不完整 | 企业预算和计费不准 | 优先使用 DSH 原生事件，缺失字段标记为未知或估算，不造假 |
| 企业管理范围膨胀 | 第一版难以交付 | 只做四类角色和最小空间模型 |
| 知识库权限复杂 | 引入过多 ACL 细节 | 第一版只做部门 / 项目空间级权限 |
| DocGraph 接口不稳定 | Adapter 频繁改动 | DocGraph 保持独立服务，Adapter 显式版本化 |
| IPD 需求尚不成熟 | 做成不可用的大系统 | 只做 Demo，不实现真实流程引擎 |
| ACP 提前接入主链路 | 后续迁移和 UI 兼容成本高 | ACP 只用于后台自动化 |
| 插件失败传染 | 一个插件拖垮主程序 | Manifest 声明依赖，启动隔离，UI 降级 |

【v1.1 新增】第二至第四行为新增风险（来源：官方桌面端仍为 prerelease、fork 成本、原生恢复动作）。

## 12. 开发计划输入建议

后续制作开发计划时，建议按以下顺序拆任务：

1. **P0 上游对齐**：基线盘点、跟随策略与差异集规格、版本锁定口径、承载机制核验、企业 bundle 预置可行性验证、账号/凭据/用量能力核验、发行与签名方案、品牌与许可、准入评审。
2. **P1 企业发行版**：上游基线可构建、差异集落地（品牌 / 更新源 / 预置 bundle）、企业入口挂载、企业凭据与诊断对齐、上游同步门禁、发行版验收。
3. **Host Core 契约冻结**：身份、空间、权限、审计、用量、插件注册、更新策略。
4. **企业插件声明规范冻结**：兼容范围、权限、UI 槽位、治理字段。
5. **P2 企业管理插件开发**：邮箱注册、组织空间、角色、审计、用量。
6. **P3 知识库 Provider 选型与空间绑定**。
7. **P4 DocGraph API 清单确认与 Adapter 开发**。
8. **P5 IPD Demo 页面与示例数据**。
9. **P6A / P6B / P6C 分别单独立项**。

进入开发前需要确认的技术项：

1. 锁定的官方桌面发行版 tag；
2. 企业预置 bundle 在官方恢复流程中的可见性（是否会被列为第三方）；
3. 官方账号登录与用量/余额能力的可用性；
4. 官方插件管理器接受的安装输入形态（私有源 / 仓库地址）；
5. 企业更新源与签名的落地方式（签名证书、更新清单路径）；
6. Electron 自动更新方案（沿用官方机制，确认我方镜像方式）；
7. P3 首选第三方知识库系统；
8. DocGraph 当前可用 API 和鉴权方式；
9. 企业模式部署拓扑：单机、局域网服务器或私有云；
10. 差异集清单与审查流程。
