# 预置插件物化进 profile `node_modules`（差异集 02/10 修正）— 交付说明

> **触发**：决策人 2026-10-12 真机截图 —— 插件市场「已安装 (3)」且三个插件都显示「启用中／已是最新」，
> 但卡片上仍有「为什么未生效？」，实际使用中**三个插件都不生效**（右侧栏增强 / Claude 皮肤 / 技能浏览器均无表现）。
> 决策人指令：「先解决插件无效问题，其它问题另起会话解决」。
> **上游基线**：`repos/deepseek-harness` @ `dsh-v0.2.1-alpha.2`（`d7432673`）
> **差异集**：02（发行物打包集成，`project-manager.ts` 调用点）与 10（升级机 profile 补齐，`profile-bundle-backfill.ts`）**同域修正**；
> 白名单归属 3.1「预置 bundle 清单」/ 3.4「企业侧默认配置」
> **门禁**：`scripts/verify_preset_plugins.py`（P3/P8 重写）、`scripts/verify_t109_profile_backfill.py`（P3/P4 扩项）

## 1. 结论先行

1. **根因（一条，两个症状）**：三个预置插件包只随**运行时树**发布（`resources/app.asar/dsh/node_modules/…`），
   既不属于安装闭包、profile 里也没有副本。而官方 `dsh-app-boot` 暴露给 profile 层的**名字解析表**只有两类：
   ① 从 `@deepseek-ai/dsh` manifest 出发的**安装闭包**（dependencies + peerDependencies）；② profile manifest 的
   **直接依赖且在 `<profile>/node_modules` 里真实存在**的名字（`collectInstallationScopePackages` /
   `installedProfilePackageNames` / `ProfileRuntimeResolution`）。三个插件两边都不占，于是：
   - 它们自己 `cordis.patch.yml` 的**裸包名行**（`dsh-better-sidebar` / `dsh-claude-style` /
     `@linxin666/dsh-client-ui-skill-explorer`）解析失败 → `entry.fiber === undefined` → 宿主 stderr 三行
     `failed to import` → 宿主半边不存在，**客户端半包自然也不进首页启动批次** → 插件完全无效果；
   - 插件市场的 `verifyActivation()` 读的是 `<profile>/node_modules/<name>/package.json` → 判 `missing`
     （「未安装」）→ 卡片显示「为什么未生效？」。**同一根因**，所以「市场说未生效」与「实际不生效」同时出现。
2. **修法**：在启动路径（`applyRelease()`，profile 锁内）把三个包**物化**进 `<profile>/node_modules`，
   形态与「市场正常安装」完全一致。规则：只在我方精确版本锚点上动作；市场/用户写过的 spec 一律不覆盖；
   本地已是随包版本则不写盘（幂等）；随包源缺失时跳过并告警、不抛错。
   **这正是 2026-10-12 早先被否决的「方案 A」**——当时否决它依据的探针证据是假的（见 §5 裁决 F-1）。
3. **验证（隔离探针，同一份安装只差「物化」这一步）**：

   | 观察面 | 物化前 | 物化后 |
   | --- | --- | --- |
   | 宿主 stderr `failed to import` | **3 行**（三条预置行） | **0 行** |
   | 首页 `__DSH_BOOT__` 含三者客户端半包 | **全 false** | **全 true** |
   | `/dsh-market/installed` 激活态 | 三条 `missing`（未安装） | 三条 `live`（已热加载 bundle patch） |

4. **真机现象已被同一 API 复现**：决策人机器上 `http://127.0.0.1:<端口>/dsh-market/installed` 返回三条
   `{"state":"missing","reasons":["未安装 / not installed"]}`，与截图逐字对应（`/dsh-market/check` 另证明三条
   bundle 行与包体都在 asar 内、`error: null`——包不缺，缺的是 profile 侧的解析锚点）。
5. **门禁不再假绿**：`verify_preset_plugins.py` 的 P8a 原断言「客户端 stderr 无 `failed to import`」**恒真**
   （Electron 壳只把宿主 stdout 转发出去，宿主 stderr 收进内部缓冲、仅在宿主非零退出时才抛出），
   P8b 又把「首页不含三方半包」解释成「按需下发」后删除。现改为：P8a 断言 profile 已物化；
   **P8b 以壳入口再起一次宿主**，断言真 stderr 无 `failed to import` + 首页含三者客户端半包 + 市场 API 判 `live`。
6. **上游零回归**：`pnpm run typecheck` exit 0；`pnpm run lint` exit 0（顺带修掉 2026-10-12 引入的
   `sonarjs(no-duplicated-branches)` 红灯，见 §5 裁决 F-4）；桌面壳套件 **125 文件通过 / 5 跳过、1425 用例通过 / 54 跳过**（1479 总数不变）。

## 4. 未验证项与边界

**需真机复核（B 类）**

- **B-1（已结案 2026-10-12）**：装机目视清单三处 —— ① 插件市场「已安装」页三条不再显示「为什么未生效？」；
  ② 右侧栏增强（内置文件渲染/终端/Git、三方新 Tab）、Claude 皮肤（设置 → 插件市场 → 主题「使用」）、技能浏览器可用；
  ③ 三插件在市场的主题/开关联动正常。**结果**：决策人装新包后回执「没有问题」；
  机器侧同步转绿 —— `verify_t112 --launch` 的 A11（新机 profile 已物化）与 `verify_preset_plugins --launch` 的 P8b
  （真 stderr 无 failed to import / 首页含三者客户端半包 / 市场判 `live`）见 V-12、V-15。
- **B-2**：**首次物化的启动耗时**未单独计时。本机 profile 的物化量 = 三个包 368 个文件 / **约 20.3 MB**
  （`dsh-better-sidebar` 17.1 MB、`dsh-claude-style` 3.0 MB、`@linxin666/…` 0.14 MB），只在缺失或版本变更时发生；
  实测启动未见异常，但未做定量对照。
- **B-3**：**市场更新路径的形态**（V-4 只覆盖「随包版本」）：市场把某插件更新到新版本后，本地副本版本与
  随包版本不同且 manifest spec 已被市场改写 → 物化**不覆盖**（按规则跳过），预期本地新版本继续生效；
  未在真机走一遍完整更新 → 重启 → 校验流程（T-121 的原始动机即此路径）。

**需外部输入（C 类）**

- **C-1**：`dshmarket` 是否跟版到 1.66.17（沿用 2026-10-12 的 C 类待定项，决策人只点名三个插件）。
- **C-2**：体积取舍（+39.4 MB 的第三方随包）——物化会让 profile 再占约 20 MB，若采纳「精简包」方案需重新评估。
- **C-3**：**预置插件是否允许「卸载」**。当前语义是「随发行版默认启用」：用户在插件市场把三者之一**卸载**后，
  它的 profile 依赖登记会消失，而启动补齐会按「我方的精确版本锚点」把依赖与 `node_modules` 副本一起补回来
  （下一次启动即恢复）。市场里的「**停用**」开关不受影响（它走禁用表，插件保持安装但关闭）。
  若决策人要支持「卸载即长期移除」，需要新增一个「已由用户移除」的标记位（新差异面，改动落在差异集 10 的文件内），
  本次不做。

**超出本次范围**

- 不修 `dshmarket`（第三方 MIT 包）本身的 `verifyActivation()` 语义：它把「安装态」定义为「profile `node_modules` 里有该包」，
  物化之后这一判据与我们的形态自然一致，无需改它。
- 不改 `packages/boot/**`（N-3）、不改上游 runtime resolution 的判据（那是官方语义）。
- 决策人点名的其它三条（遗留文档补提交、`dshmarket` 跟版、T-022/T-025/T-028/T-080 既有红灯校正）**按指令另起会话**。

## 5. 裁决记录

| # | 裁决：<决定> — <理由> — <错判代价> |
| --- | --- |
| F-1 | **推翻 2026-10-12 早先的 M-11（「不做 profile 物化」），改为在启动路径物化** — M-11 的依据是「隔离 DSH_HOME 启动桌面壳，三条预置行 `failed to import` = 0」，但那条探针读的是**客户端自己**的 stderr，而 Electron 壳只转发宿主 stdout（`child.stdout.pipe(process.stdout)`）、把宿主 stderr 收进内部缓冲只在非零退出时才抛出 → 该断言**恒真**。以壳入口直接起宿主后，同一份安装的宿主 stderr 就是三行 `failed to import`，首页也没有三者客户端半包（探针 A/B 对照）。同时 M-11 把「首页不含三方半包」解释为「按需下发」也与实现不符：行一旦 live，其客户端半包就进首页启动批次 — 若不推翻，三个插件会长期「显示已启用、实际不生效」，并把真实缺陷写成「已结案」（代价：用户侧功能长期缺失 + 一条错误结论留在文档里） |
| F-2 | **修法取「物化进 profile `node_modules`」而不是「让三包进安装闭包」** — 闭包路线能修宿主侧解析，但插件市场的生效判据读的是 profile `node_modules`（V-1），闭包路线下市场仍会显示「未安装/未生效」，用户看到的症状只修一半；物化与「市场正常安装」同形，两个症状一次修好，且让市场的更新优先级（本地优先）保持官方语义 — 若只走闭包，市场 UI 会继续误报（代价：一轮返工 + 用户继续踩同一坑） |
| F-3 | **物化只在「我方精确版本锚点」上动作**（缺失 → 写；manifest spec 不等于随包版本 → 不动本地副本） — 市场/用户装过的版本不能被随包版本悄悄覆盖，否则「更新到新版 → 重启被回退」是更严重的隐性回归；反过来若锚点是我们自持的精确版本且本地是旧版本，同步为随包版本才是正确语义（沿用 M-12 的锚点口径） — 若粗暴覆盖，市场升级会被静默回退（代价：一次用户可见的版本回退事故） |
| F-4 | **顺手修掉 `backfilledPresetDependencies()` 的 `sonarjs(no-duplicated-branches)` 红灯** — 该红灯由 2026-10-12 的 M-12 改动引入（两个分支体相同），本轮 `--full` 门禁复跑暴露；修法只是把两个等价分支合并成一个条件，语义逐字不变 — 若不修，`verify_t020_build.py --full` 持续红灯，lint 门禁失去信号意义（代价：门禁长期假红） |
| F-5 | **门禁 P8b 改为「以壳入口起宿主 + 三面断言」**，而不是继续登记为 B 类目视 — 目视不可机检、且上一轮正是靠「探针恒真 + 目视待办」把缺陷掩盖过去；壳入口可直接以 `--expose-internals <dsh-desktop-host>/lib/index.js` 起（与客户端同一 argv/环境），宿主会把带 token 的 URL 打到 stdout，因此探针无需 GUI — 若不改，同一类缺陷下次仍会以「门禁全绿 + 目视未做」的形态漏出去（代价：重复一次线上可见的功能缺陷） |
